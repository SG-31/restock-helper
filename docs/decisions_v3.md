## 1. アプリ概要

一人暮らしの高齢者向け：ヘルパーが週1回入力する在庫データから、
次回買い出しまでに必要な補充量を自動計算し、買い物リストを作成するアプリ。

**このアプリの本質**：実店舗への自動発注・決済ではなく、
「在庫確認 → 使用量の算出 → 適正在庫の調整 → 補充量の算出 → 買い物リスト作成」
という一連の支援を行うもの。作成されたリストは、ヘルパーが実際に買い出しに行く際の
参考情報として使う（アプリの外で人が買い物する）。

学習目的：初心者ポートフォリオとして、Python/Flask/SQLiteの技術学習を兼ねる。

## 2. アクター構成（確定）

2人体制、役割分担あり：

| アクター | 役割 |
|---|---|
| 高齢者本人 | 買い物リストを確認し、在庫管理はしていない品目を「今回だけ買ってほしいメモ」として自由に書き足せる（在庫の記録・追跡は行われない。品目マスターへの登録ではない） |
| ヘルパー | 週1回訪問時に、管理品目の在庫数を入力する。買い物完了後に「買い物完了」を記録する |

- ログイン機能：MVPでは省略（自分専用端末での利用を想定、`AI推測`）
- 「今アクセスしているのが誰か」を区別する仕組みは、7-1のトップ案内画面（`/`）から、
  それぞれの画面URLへ移動する形で対応することとした（詳細は7-1参照）

## 3. 適正在庫の計算ロジック（確定）

```
週間消費量 = max(0, 前回入力時の在庫数 − 今回の在庫数)
移動平均消費量 = 直近4週間分の週間消費量の平均（データが4回未満ならある分だけで平均）
適正在庫数 = 移動平均消費量 × 1.5（1.5週間分の安全バッファ）
補充必要数 = 適正在庫数 − 現在庫数（マイナスなら0）
```

**決定理由**：
- 平均期間を4週間にしたのは、3回だと1回の異常値（来客等で消費が増えた週）の影響が大きすぎるため（重み33%→25%に緩和）
- バッファ係数は当初1.2（1週間分+20%）を仮採用していたが、「急な使用量増加でも欠品しにくくしたい」という意図から**1.5に変更**（下記3-4参照）
- この数値（1.5）は統計的に厳密な根拠ではなく、初期仮説値。実データを見ながら調整する前提（面接で聞かれた場合はこの経緯を正直に説明する）

### 3-4. バッファ係数の検討経緯（1.2 → 1.5に変更・確定）

`AI推測`（計算式は`確定事実`として検証済み）

係数ごとに「平均消費量に対して何%の急増まで欠品しないか」を比較：

| 係数 | 意味 | 耐えられる急増の目安（平均比） |
|---|---|---|
| 1.2 | 1週間分＋20%の余裕 | +20%まで |
| **1.5（採用）** | 1.5週間分の在庫 | **+50%まで** |
| 2.0（不採用） | 2週間分の在庫 | +100%まで |

- 1.2は在庫の積み上がりは少ないが、来客等による急な消費増加に弱い
- 2.0は欠品リスクは低いが、「買いすぎ」状態を再現してしまうため不採用（3章オリジナルの決定理由）
- **1.5はこの中間**：欠品耐性を上げつつ、2.0ほど極端に在庫が積み上がらないバランスとして採用

**トレードオフとして残る点**：1.2よりは在庫が多めに積み上がる方向に働く。この点は実データを見ながら調整する。

### 3-1. 初回登録時の扱い（確定）

**運用フロー**：ヘルパーは「買い出しを終えた直後」に管理品目を登録する（品目名・単位・**買い出し後の在庫数**を初期値として入力）。

- **week 0（登録日）**：初期在庫数を記録。これが最初の「前回値」として使える
- **week 1（1週間後の訪問）**：ヘルパーが在庫数を入力 → `week0の在庫 − week1の在庫` で最初の週間消費量が計算できる → **この時点から買い物リストの提示が始まる**

`一般的な慣習（未検証）`：買い出し直後に登録する運用にすることで、初期在庫が「満タンに近い状態」になり、最初の消費量データが異常値になりにくい。逆に在庫が少ないタイミングで登録すると、初期の適正在庫数が過小評価されるリスクがある。この運用ルールをREADME・ユースケース①の前提条件に明記する。

### 3-2. マイナス消費量（在庫が増えた場合）の扱い（確定）

**結論：週間消費量がマイナスになった場合は「使用量0」として扱い（0にクリップ）、移動平均の計算には含める。**

`AI推測`

- 在庫が増えるケースは、システムを通さない補充（家族の差し入れ等）が起きたことを示す可能性が高い
- マイナス値をそのまま平均に含めると消費量が過小評価され、補充判定が歪む。0クリップの方がシンプルで実害も小さい

**検討したが採用しなかった案**：マイナスになった週を移動平均の計算対象から「除外」する方式。理論上はより正確な消費ペースが出せるが、「直近4週間」ではなく「直近の有効な4週間」を数える処理が必要になり、全週マイナスの場合のフォールバックも考慮する必要が出るなど、実装がやや複雑になるため見送り。→ 8-2「あったら嬉しい機能」に追記。

### 3-3. 週次スナップショット方式の限界（認識事項）

`一般的な慣習（未検証）`：このアプリは週1回の在庫スナップショットしか見ていないため、1週間の間に起きた「純粋な消費」と「ヘルパー以外による買い足し」は区別できず、差分としてまとめて観測される。これはMVPとして受け入れる制約とし、README等に明記する。

### 3-5. 「買ってほしいもの」の呼称・配置（確定）

**結論**：管理外品目（自由メモ）は、UI上「その他の商品」ではなく**「買ってほしいもの」**と表記する。追加ボタンは買い物リスト画面（`/list`）内に設置する。

**決定理由**：「その他の商品」という呼称は、管理品目のマスター登録と混同されやすい（実際に検討中、AIが誤って両者を同一視したケースがあった）。「買ってほしいもの」とすることで、「在庫管理しない、今回限りのメモ」という性質が伝わりやすくなる。目的（買い物を頼む）と操作（リストに書き足す）を同じ画面にまとめることで、操作ステップも増えない。

### 3-6. 在庫保存後の画面遷移・買い物完了の確定方法（確定）

**結論**：
1. ヘルパーが在庫を保存すると、`/input`内で「在庫を更新しました」という確認メッセージと、更新後の買い物リスト（補充が必要な品目）を**同じ画面に表示**する（`/list`へは遷移しない。ヘルパー用画面の中で完結させる）
2. この画面に「買い物完了」ボタンを設置するが、押しても即座には確定させず、**確認ダイアログを1回挟む**

```
/input
在庫入力 → ［保存］
   ↓
自動計算
   ↓
「在庫を更新しました」＋ 買い物リスト表示
   牛乳　2本
   卵　　6個
   ［買い物完了］
   ↓
「今週分として更新しますが、よいですか？」
   ［はい］／［キャンセル］
```

**決定理由**：
- 「入力完了画面のみ表示」→「保存後すぐに買い物リストも見せる」に変更。ヘルパーの目的は「在庫を保存すること」自体ではなく「何を買うべきか確認すること」であるため、1画面で完結させる方が自然
- 別ルート（`/input/complete`等）に分ける案も検討したが、URL・画面が増えるため、今回のMVP規模には過剰と判断し不採用
- 「買い物完了」は表示数量をそのまま購入数量として在庫に反映する、後戻りしにくい重要な操作（4章参照）。保存ボタンと同じ感覚で押せてしまうと、在庫データが実態とズレたまま次週の消費量計算に使われ、気づきにくいエラーにつながる。そのため確認ダイアログで一段階の意思確認を挟む
- **確認ダイアログの文言は「今週分として更新しますが、よいですか？」に変更した（v3.0で確定）**。「今週分」という言葉を入れることで、まだ入力途中の状態で誤って保存・完了操作をしてしまうことへの注意喚起も兼ねる（3-7・9章参照）

**買い物完了の一連の流れ（v3.0で明確化）**：
```
1. ヘルパーは /list を見ながら実際に店で購入する
2. 購入後、/input に戻り「買い物完了」ボタンを押す
3. 確認ダイアログ「今週分として更新しますが、よいですか？」
4. 「はい」の場合、current_stockに補充必要数を加算し、
   shopping_memosを全削除する
5. 完了後は /input にとどまる（別画面へは遷移しない）
```

**決定理由**：買い物完了という「ボタンを押す操作」自体は`/input`画面にあるが、それは「`/list`を見て、実際に買い物を終えた後、最後の確定作業として`/input`に戻ってくる」という一連の流れの最終ステップである。完了後`/input`にとどまることで、更新された在庫数や、空になった買い物リストを、ヘルパー自身がその場で確認できる。

### 3-7. 管理品目の変更・削除（確定）

**結論**：管理品目の「変更」「削除」機能を追加する。削除は**物理削除**（過去の消費量データも一緒に削除される）とし、削除ボタンに警告を表示する。

**決定理由**：
- 登録機能をすでに作る前提なので、変更・削除は既存の画面・処理を流用でき、追加コストは小〜中程度
- 過去データの厳密な保全よりも「今使う分の買い物リスト作成」を目的とするアプリの性質上、論理削除（データを残したまま非表示にする）のような複雑な仕組みは不要と判断
- 品目はID管理を前提とするため、名前変更をしても過去の消費量データとの紐付けは保たれる（品目IDを主キーとして実装済み）
- CRUD（登録・参照・更新・削除）を一通り実装した経験として、ポートフォリオ的にもプラスに働く

**注意点**：削除ボタンには「削除すると、この品目の過去の消費量データも消えます」という警告を表示する（最低限のデータ保護配慮として）。

### 3-8. 補充必要数の端数処理（v3.0で新規確定）

**結論**：補充必要数（適正在庫数 − 現在庫数）に小数が生じる場合は、**切り上げ**て整数化する。

**決定理由**：
- `items.current_stock`はINTEGER型（8-3参照）であり、買い物完了時にこの値へ加算する数量は整数である必要がある
- 3-4で確定したバッファ係数1.5の考え方（欠品耐性を優先する）と一貫性を持たせるため、端数は切り捨てず切り上げる方式を採用した
- 実装は`calculations.py`の`calc_required_quantity()`内で`math.ceil()`を用いて行う（8-6参照）

### 3-9. consumptionsが0件の品目の扱い（v3.0で新規確定）

**結論**：ある品目について`consumptions`（消費量データ）が1件も存在しない場合、その品目は買い物リストの計算対象外とする（補充必要数を計算せず、リストにも表示しない）。

**決定理由**：
- 3-1で確定した運用フロー上、「week1（1回目の在庫入力）」を経るまでは、そもそも消費量データが存在しない
- 移動平均を「0」として計算しても最終的な補充必要数は0になり結果は同じだが、実在しないデータをもとに計算したという扱いを避け、「判定できるデータがまだない」という意図をコード上でも明確にするため、計算そのものをスキップする設計とした（`calculations.py`の`calc_moving_average()`は空リストに対して`None`を返す）

## 4. 要件リスト（確定）

### 必須機能
- 管理品目の登録（品目名、単位、初期在庫数）
- 管理品目の変更（品目名・単位等の編集）
- 管理品目の削除（物理削除。削除すると過去の消費量データも消える旨の警告を表示する。詳細は3-7参照）

- 入力のたびに週間消費量を記録

- 次回買い出し用リストの表示（管理品目の補充分＋メモ品目）
- 「買い物完了」操作（表示された数量＝購入した数量として扱う。実購入数量の別途入力はしない）。確認ダイアログを挟んで確定する（確定。3-6参照）
- **トップ案内画面（`/`）の表示（v3.0で追加。7-1参照）**
- **在庫入力時の誤操作防止（変更行のハイライト、確認ダイアログ、ボタン無効化。v3.0で追加。9-1参照）**

### あったら嬉しい機能（後回し）
- 消費傾向のグラフ表示
- 買い出し完了後にメモ品目をクリア（実装済み。3-6参照）
- リストの印刷・PDF出力
- 消費量のブレ幅（分散）を見た自動調整の高度化
- マイナス消費量になった週を移動平均の計算対象から除外する方式（3-2参照。現在は0クリップで簡易対応）

- 誤った消費量履歴の訂正機能（現時点では未実装。誤入力時は現在庫の再入力で対応可能。訂正が必要な誤操作は稀と想定し、優先度は低いと判断。詳細は9-2参照）

### 初期バージョンで作らない機能（明示的に対象外）
- 実際の宅配業者との連携・注文送信・決済
- 会員登録・複雑なログイン
- メッセージ機能・複雑な通知
- AIによる高度な需要予測
- 家族との共有機能
- **複数世帯対応**（検討済み。認証（ログイン機能）を足すだけでは不十分で、全テーブルへの`household_id`（世帯を識別する列）の追加、全SQL文への世帯単位の絞り込み条件の追加、ヘルパーが複数世帯を掛け持ちする場合の「担当世帯を選ぶ」仕組みなど、実装量がMVPの2〜3倍規模に膨らむ拡張と認識している。現在のアプリは1世帯専用として設計）

## 5. ユースケース（確定）

### ユースケース①：ヘルパーが在庫を入力する
**アクター**：ヘルパー　**事前条件**：管理品目が最低1つ登録されている（登録は買い出し直後、買い出し後の在庫数を初期値として行う。詳細は3-1参照）

基本フロー：
1. ヘルパーは「在庫入力」画面（`/input`）を開く
2. システムは管理品目と前回登録在庫数を表示
3. ヘルパーは実際の在庫数を入力（変更した行は背景色で強調表示される。9-1参照）
4. 「保存」を押す（確認ダイアログ「今週分として更新しますが、よいですか？」が表示される。3-6・9-1参照）
5. システムが週間消費量・移動平均・適正在庫数を更新
6. 補充必要数を反映した買い物リストを再生成
7. 同じ画面（`/input`）内に「在庫を更新しました」と更新後の買い物リストを表示（`/list`へは遷移しない。詳細は3-6参照）

代替フロー：
- 入力を飛ばした品目 → 前回値を保持、消費量計算はスキップ（0扱いにしない）
- 不正な値（マイナス等） → 警告表示、保存を防ぐ

### ユースケース②：利用者が買い物リストを見る
**アクター**：高齢者利用者　**事前条件**：最低1回、在庫入力が行われている

基本フロー：
1. 利用者は「買い物リスト」画面（`/list`）を開く
2. システムは補充が必要な管理品目を一覧表示
3. 利用者は「＋買ってほしいものを追加」から、管理外品目（メモ）を自由に追加
4. システムはメモをリストに反映
5. 利用者はリストをヘルパーに見せる

代替フロー：
- 補充が必要な品目が0件 → 「補充が必要なものはありません」と表示

### ユースケース③：ヘルパーが買い物を完了する
**アクター**：ヘルパー　**事前条件**：買い物リストが表示されている（ユースケース①の続き）

基本フロー：
1. ヘルパーは`/list`を見ながら、買い物リストに表示された品目を実際に購入する
2. `/input`画面に戻り、「買い物完了」ボタンを押す
3. システムは確認ダイアログ「今週分として更新しますが、よいですか？」を表示
4. ヘルパーが「はい」を選択
5. その時点で再計算された補充必要数が、そのまま購入数量として在庫に反映される
6. 管理外品目（メモ）はリストから消える
7. 完了後、画面は`/input`にとどまる（詳細は3-6参照）

代替フロー：
- 「キャンセル」を選択 → 何も確定せず画面に留まる（詳細は3-6参照）

### ユースケース④：利用者が「買ってほしいもの」を削除する
**アクター**：高齢者利用者　**事前条件**：買い物リストに、利用者が追加したメモが1件以上ある

基本フロー：
1. 利用者は「買い物リスト」画面（`/list`）を開く
2. メモ品目の横にある「削除」を選択
3. システムはリストからそのメモを削除する

代替フロー：
- 存在しないメモIDが指定された場合 → サーバーエラーにならず、404等の適切な応答を返す

### ユースケース⑤：ヘルパーが管理品目を登録する
**アクター**：ヘルパー　**事前条件**：なし

基本フロー：
1. ヘルパーは品目管理画面を開く

**アクター**：ヘルパー　**事前条件**：変更したい管理品目が1つ以上登録されている

4. システムは変更内容を反映する（過去の消費量データとの紐付けは品目IDで維持される）

**アクター**：ヘルパー　**事前条件**：削除したい管理品目が1つ以上登録されている

## 6. 技術構成（確定）

**方式A：複数端末でサーバー・DBを共有**

```
[サーバー：自分のPC → 最終的にクラウド]
   Flask（Webフレームワーク）+ SQLite（DB）
        ↓（ブラウザでアクセス）
[高齢者のスマホ]　　[ヘルパーのスマホ]
```

- 開発中はローカルPCでFlaskを起動して動作確認
- 完成後、クラウド（Render, Railway等の無料枠を想定）にデプロイして公開
- **クラウドDBの選定（確定）**：開発中はSQLiteを使用し、クラウド公開時にPostgreSQLへ移行する。理由：SQLiteはファイルベースのDBのため、無料ホスティングでは再起動・再デプロイ時にデータが失われるリスクがあり、また複数ユーザーの同時アクセスにも弱い。PostgreSQLはサーバー型DBで、クラウドWebアプリとの相性が良く、複数ユーザーからのアクセスにも強い。移行コストを抑えるため、SQLite→PostgreSQLへの変更が小さく済むように設計する（具体的にはSQL文をなるべく標準的な書き方にする）
- **デプロイ前の対応事項（v3.0で追記）**：`app.run(debug=True)`のまま公開すると、詳細なエラートレース情報が外部に見える状態になり、セキュリティ上のリスクがある。クラウドへのデプロイ時には、必ず`debug=False`に変更すること（9-4・静的解析でも検出済みの項目）

**使用技術**：Python, Flask, HTML, CSS, SQLite, SQL, Git/GitHub

**選定理由**：2アクター（高齢者・ヘルパー）が別々の端末から同じデータを見る必要があるため、サーバー・DB構成がほぼ必須。ローカル完結型（単一HTML等）では複数端末間のデータ共有ができない。

### 7-1. 画面一覧

MVPとして、以下の**5画面構成**とする（削除は独立画面にせず確認ダイアログで対応）。

| No. | 画面 | URL | 主な利用者 | 目的 |
|---|---|---|---|---|
| 0 | トップ案内画面 | `/` | 全員 | 各画面（`/list`, `/input`, `/items`）への入口を示す簡易ページ |
| 1 | 高齢者用・買い物リスト | `/list` | 高齢者 | 買い物リストの確認・「買ってほしいもの」の追加・削除 |
| 2 | ヘルパー用・在庫入力 | `/input` | ヘルパー | 週1回の在庫入力、保存後は同画面に買い物リストを表示、買い物完了もここで行う |
| 3 | 管理品目一覧 | `/items` | ヘルパー | 管理品目の確認、登録・変更・削除への入口 |
| 4 | 管理品目登録・編集 | `/items/new`、`/items/<id>/edit` | ヘルパー | 管理品目の登録・変更（同じフォーム構造を流用） |

**決定理由（v2.3時点）**：
- ホーム画面（全体のトップメニュー）は作らない。すでにURLを高齢者用（`/list`）とヘルパー用（`/input`）で分けている（2章）ため、共通の入口を別途作る必要がない
- 削除確認は別画面にせず確認ダイアログにする（3-6・3-7の確認ダイアログ方針と一貫）
- 登録・変更フォームは共通化し、画面数を増やさない

**トップ案内画面（`/`）の追加について（v3.0で確定）**：
- 実際の利用時は、スマートフォンのホーム画面にアイコンを追加して開く運用を想定している。当初「ホーム画面（トップメニュー）は作らない」としていたが、初回アクセス時や、目的の画面のURLを忘れた場合の導線として、`/`に3つのリンク（`/list`, `/input`, `/items`）を並べただけの簡易案内ページを追加する
- これは複雑な状態管理（通知、履歴、ログイン状態等）を持つトップメニューではなく、静的なリンク集であるため、上記の「ホーム画面は作らない」というもともとの決定理由（共通の入口を別途作る必要がない、という判断）と大きく矛盾するものではないと位置づける
- 各画面（`/list`, `/input`, `/items`, `/items/new`, `/items/<id>/edit`）にも、`/`へ戻るリンクを設置する

### 7-2. 画面遷移

```
トップ案内画面（/）
  ├── /list へ
  ├── /input へ
  └── /items へ

高齢者
  └── /list
        ├── 買い物リストを見る
        ├── 「買ってほしいもの」を追加
        ├── 「買ってほしいもの」を削除
        └── トップに戻る（/）

ヘルパー
  ├── /input
  │      ├── 在庫を入力 → 保存確認ダイアログ → 保存 → 自動計算
  │      ├── 更新された買い物リストを同画面に表示（3-6）
  │      ├── 買い物完了（確認ダイアログを挟む。3-6）
  │      └── トップに戻る（/）
  │
  └── /items
         ├── 管理品目一覧を見る
         ├── 登録（/items/new）→ マイナス値は警告・保存不可
         ├── 変更（/items/<id>/edit）
         ├── 削除（確認ダイアログ）→ 品目と紐づく消費量データを物理削除（3-7）
         └── トップに戻る（/）
```

**注意（用語の統一）**：削除確認ダイアログで消えるのは**消費量データのみ**（3-7）。在庫数そのものを週ごとに履歴保存する仕組みはこのアプリには存在しないため、「在庫データも削除される」という表現は使わない。

### 7-3. 現在庫の持ち方・買い物完了時の購入数量の確定方法（確定）

**結論**：

- **現在庫数**は、管理品目1件につき**1つの値のみ**を持つ（週ごとの在庫履歴は保存しない。3-3と一致）。`/input`で在庫を保存するたびに上書きする
- **前回在庫（消費量計算用）は別途保存しない**。上書きされる直前の「現在庫数」の値を、そのまま前回値として使う
  ```
  ① 現在庫数を読む（＝前回値）
  ② 週間消費量 = max(0, 前回値 − 今回入力値) を計算し、消費量データとして保存
  ③ 現在庫数を今回入力値に上書きする
  ```
- **補充必要数（買い物リストに表示する数量）はDBに保存しない**。移動平均×1.5－現在庫数、の計算式（端数は切り上げ。3-8参照）で都度算出する
- **買い物完了時の購入数量も保存せず、完了操作の時点でもう一度同じ計算式を実行して求める**。この数量を現在庫数に加算する
  ```
  買い物完了時：現在庫数 = 現在庫数 + （その時点で計算した補充必要数）
  ```

**決定理由**：
- 3-3で「週次スナップショットしか見ない」ことをすでに受け入れているため、在庫数を1つの値として持ち、毎回上書きする方式が既存の方針と一貫している
- 補充必要数・購入数量は、その場で再計算すれば必ず同じ値が求まる（＝保存しなくても失われる情報がない）ため、DBをシンプルに保てる

**前提（重要）**：この「その場で再計算する」方式が安全に成立するのは、「在庫保存」から「買い物完了」までの間、現在庫数を変更できる操作が他に存在しないためである（`/list`側の「買ってほしいもの」追加・削除は現在庫数に影響しない）。MVPでは、同じ品目を複数のヘルパーが同時に編集する状況は想定しない。将来、複数人による同時編集を想定する場合は、この前提が崩れるため、購入数量を買い物リスト生成時点で確定値として保存する設計に見直す必要がある。

## 8. DB設計（確定）

### 8-1. テーブル一覧

MVPでは3テーブルで構成する。「買い物リスト」専用のテーブルは作らない（補充必要数は保存せず、都度計算する。7-3参照）。

| テーブル名 | 役割 |
|---|---|
| `items`（管理品目） | 継続的に在庫管理する商品。現在庫数を1件につき1つだけ保持 |
| `consumptions`（消費量データ） | 毎週の入力から算出された週間消費量の履歴 |
| `shopping_memos`（買ってほしいもの） | 高齢者が追加する、今回限りの自由メモ。管理品目とは関連付けない |

### 8-2. テーブル同士の関係

```
items（管理品目） 1 ── 多 consumptions（消費量データ）

shopping_memos（買ってほしいもの） … 独立（他テーブルと関連付けしない）
```

### 8-3. カラム定義

**items**

| カラム | 型 | 内容 |
|---|---|---|
| `id` | INTEGER | 品目ID（主キー） |
| `name` | TEXT | 品目名 |
| `unit` | TEXT | 単位（本、個、kgなど） |
| `current_stock` | INTEGER | 現在庫数（7-3の通り、履歴は持たず1値のみ。整数のみ許容。3-8参照） |
| `created_at` | TEXT | 登録日時 |
| `updated_at` | TEXT | 更新日時（アプリ側で更新のたびにセットする。DBの自動更新機能ではない） |

**consumptions**

| カラム | 型 | 内容 |
|---|---|---|
| `id` | INTEGER | 消費量データID（主キー） |
| `item_id` | INTEGER | 外部キー（`items.id`） |
| `consumption` | INTEGER | 週間消費量（3-2の通り、マイナスは0クリップして保存） |
| `recorded_at` | TEXT | 記録日時 |

**shopping_memos**

| カラム | 型 | 内容 |
|---|---|---|
| `id` | INTEGER | メモID（主キー） |
| `text` | TEXT | 高齢者が入力した内容 |
| `created_at` | TEXT | 追加日時 |

### 8-4. CREATE TABLE文（SQLite）

```sql
CREATE TABLE items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    unit TEXT NOT NULL,
    current_stock INTEGER NOT NULL CHECK (current_stock >= 0),
    created_at TEXT NOT NULL DEFAULT (CURRENT_TIMESTAMP),
    updated_at TEXT NOT NULL DEFAULT (CURRENT_TIMESTAMP)
);

CREATE TABLE consumptions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id INTEGER NOT NULL,
    consumption INTEGER NOT NULL CHECK (consumption >= 0),
    recorded_at TEXT NOT NULL DEFAULT (CURRENT_TIMESTAMP),

    FOREIGN KEY (item_id) REFERENCES items(id) ON DELETE CASCADE
);

CREATE TABLE shopping_memos (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    text TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (CURRENT_TIMESTAMP)
);
```

**アプリ起動時に必ず実行する（実装済み）**：
```sql
PRAGMA foreign_keys = ON;
```
SQLiteは`ON DELETE CASCADE`を書くだけでは自動的に有効にならず、上記の設定を毎回実行しないと連動削除が働かない。**v3.0では、この設定漏れを構造的に防ぐため、`db.py`の`get_connection()`に一本化した（8-6参照）。**

### 8-5. 決定理由・設計方針

- **保存するもの**：品目情報・現在庫数・週間消費量・買ってほしいものメモ
- **保存しないもの**：移動平均、適正在庫数、補充必要数、買い物リストそのもの（いずれも必要な時に計算式から求める。7-3参照）
- **CHECK制約**：`current_stock >= 0`、`consumption >= 0`は、アプリ側のバリデーション（マイナス値→警告・保存不可、3-2）と二重に保護するため、DB側にも設定する
- **`ON DELETE CASCADE`**：3-7（品目削除時に紐づく消費量データも物理削除）と一致させるため採用
- **日時の形式**：ISO 8601形式（例：`2026-08-30 21:15:00`）で統一する。文字列のまま時系列ソートが可能で、将来PostgreSQLの`TIMESTAMP`型へ移行しやすいため

### 8-6. 実装方針（v3.0で更新）

- **ORM（SQLAlchemy等）は当面導入しない。** Pythonの標準ライブラリ`sqlite3`を使い、生のSQLを直接書く。理由：SQLite→PostgreSQL移行時の書き換えコストより、まず「Python→SQL→SQLite」の関係を自分の手で理解することを学習目的として優先する。将来PostgreSQLへの移行時に、必要であればあらためて検討する

- **ファイル構成（v3.0で確定・変更）**：機能ジャンル単位でファイルを分割する構成に変更した。MVCのフォルダ構造（`models/`・`views/`・`controllers/`）は採用しないが、`app.py`肥大化への対応として以下の構成とした。

```
restock-helper/
├─ app.py                    # Flask起動、DB初期化、Blueprint登録のみ
├─ db.py                     # DB接続の共通処理（get_connection()）
├─ calculations.py           # 補充必要数の計算ロジック（DB非依存の純粋関数）
├─ routes/
│   ├─ __init__.py
│   ├─ items.py              # 管理品目のルート＋DB操作（CRUD）
│   ├─ stock.py              # 在庫入力（/input）のルート＋DB取得
│   └─ shopping.py           # 買い物リスト（/list）・買い物完了のルート＋DB操作
├─ requirements.txt
├─ pyproject.toml            # ruff設定含む
├─ .gitignore
├─ database/
│   └─ restock.db
├─ templates/
│   ├─ index.html            # トップ案内画面
│   ├─ list.html
│   ├─ input.html
│   ├─ items.html
│   └─ item_form.html
└─ static/
    └─ style.css
```

**決定理由（役割分担）**：
- `db.py`：DB接続処理（`sqlite3.connect()`, `PRAGMA foreign_keys = ON`, `row_factory`設定）を1箇所に集約した。理由：SQLiteは接続ごとにPRAGMA設定が必要であり、複数箇所に接続処理をコピーすると設定漏れが起きやすい（実際にレビューで指摘された問題）。共通関数化することで、この種の書き忘れを構造的に防げる
- `calculations.py`：補充必要数の計算ロジック（移動平均・適正在庫数・補充必要数の算出）を、DBに一切依存しない純粋関数として独立させた。理由：`/input`（`routes/stock.py`）と`/list`（`routes/shopping.py`）の両方で同じ計算が必要になるが、それぞれのファイルに計算ロジックを別々に書いてしまうと、修正時に一方だけ直し忘れ、画面ごとに異なる計算結果が表示される不具合が実際に発生した。計算処理を1箇所（`calculations.py`）に一本化することで、この種の不一致を構造的に防止する
- `routes/*.py`：ルーティング（URLの入口）とDB操作は、機能ジャンルごとに1ファイルにまとめた。理由：役割ごとに細かく分割しすぎると、1つの機能を追うのに複数ファイルを行き来する手間が増える。今のプロジェクト規模（画面5つ、テーブル3つ）では、「品目のことは`items.py`を見ればすべて分かる」という状態の方が保守しやすいと判断した

- **フォルダ構成は厳密なMVC（`models/`・`views/`・`controllers/`）には分割しない。** 理由：画面5つ・テーブル3つというMVPの規模に対し、厳密なレイヤー分割は過剰設計になりやすく、「なぜこの分割にしたか」を説明しにくくなる。機能が大きく増えた場合は、その時点で段階的に整理する（Flaskの`Blueprint`機能は導入済み）

## 9. AI活用プロセスの振り返り（記録）

開発の過程で起きた「AIとの協働の失敗と改善」の実例。ポートフォリオとして、単に動くアプリを作っただけでなく、**AIを使った開発プロセス自体をどう改善したか**を示す記録として残す。

### 9-1. 経緯：エラー処理の指示漏れ

`確定事実`

②AI（実装担当）へテーブル作成・DB接続確認の実装を依頼した際、プロンプトに「エラー処理（try/except）を入れること」を明記し忘れていた。プロジェクトの基本方針には「例外処理を、握りつぶさず適切に行う」という**常に守るべきルール**として最初から明記されていたにもかかわらず、実装プロンプトを作成する際にこのルールとの照合を怠っていた。

**気づいたきっかけ**：ユーザーから「Flask・DB接続確認のコードにエラー処理は不要か」と質問を受け、Claude側の見落としであったことが判明した。

### 9-2. 原因の分析

`AI推測`

Claudeの意識が「②AIの提案とdecisions.mdとの整合性チェック」に強く向いており、**プロジェクトの基本方針そのものへの照合という、もう1段階手前のチェックが手薄になっていた**ことが原因と考えられる。個別の設計判断のレビューに気を取られ、常時適用されるべき基本ルールの確認が形骸化していた。

### 9-3. 対処：チェックリスト運用の導入

再発防止のため、②AIへの実装プロンプトを作成する際、以下の基本チェックリスト（プロジェクトの基本方針より抜粋）と必ず照合してから提示する運用に変更した。

```
実装プロンプトを作る前の確認チェックリスト
□ パスワード・APIキー・トークンを直接コードに書いていないか
□ 外部入力（ユーザー入力等）を無条件に信頼する設計になっていないか
□ 例外処理（try/except）が必要な箇所は明記したか
□ .gitignoreで秘密情報が除外される設計になっているか
```

また、学習者向け資料（SCAO learning kit）で紹介されていた「生成AIへの指示の8要素」（目的・背景/前提・対象範囲・変更禁止範囲・完了条件・検証方法・停止条件・出力形式）のうち、特に**完了条件**（例：「エラー時に適切なメッセージが表示されること」）に非機能要件を含めることで、同種の見落としを構造的に防ぐ方針とした。

### 9-4. 副次的な効果：静的解析ツール（ruff）による裏付け

上記の対応と並行して、Cursorにruff拡張機能を導入し、`pyproject.toml`でセキュリティ関連ルール（`S`、flake8-bandit相当）を有効化した。その結果、`app.py`から**Flaskの`debug=True`使用（`S201`）**が実際に検出された（`03_DATA_AND_SECURITY_DESIGN.md` Open Issues TBD-003参照）。

これは「AIプロンプトでの事前チェック（人間・AIによるレビュー）」と「静的解析ツールによる機械的な検出」を組み合わせることで、**指示の抜け漏れとコード上の問題の両方に、異なる仕組みで気づける体制になった**ことを示す実例である。

**ポートフォリオとしての位置づけ**：単なる失敗談ではなく、「AIに実装を任せる際、指示の抜け漏れがどう発生し、どう仕組みで防ぐか」を実体験として説明できる材料として記録する。

### 9-5. 計算ロジックの重複による不具合（v3.0で追記）

`確定事実`

`/input`（在庫入力画面）と`/list`（買い物リスト画面）で、同じ品目に対する補充必要数の表示が異なる（例：`/input`では3.5、`/list`では4）という不具合が実際に発生した。

**原因**：`routes/stock.py`（当時）に、DBから消費量を取得し移動平均・補充必要数を計算するロジックが独自に実装されており、一方で共通化を意図して作成した`calculations.py`にも同様の計算関数が存在していた。計算ロジックが2箇所に別々に存在していたため、一方にのみ端数処理（切り上げ）を追加した際、もう一方に反映されず、不一致が生じた。

**対処**：`routes/stock.py`側の独自計算処理を廃止し、DBから消費量データを取得する処理のみを残した上で、計算そのものは必ず`calculations.py`の関数を呼び出す形に修正した（8-6参照）。また、紛らわしかった関数名`calculate_restock_amount()`（実際にはDB取得＋委譲を行う窓口関数）を`get_consumptions()`に変更し、「計算する関数」と「取得して渡すだけの関数」が名前からも区別できるようにした。

**教訓**：「同じ処理を複数箇所にコピーして書くと、片方だけ修正して不整合が生じるリスクがある」という、9-1のエラー処理漏れと同種の問題が、計算ロジックでも発生しうることを実体験として確認した。共通化する際は、呼び出し元をすべて実際に共通関数経由に置き換えたかを確認する必要がある。

### 9-6. 誤操作対策の検討（v3.0で追記）

`確定事実`

実際にテスト運用を行う中で、以下の2つの誤操作パターンが見つかった。

1. `/input`で保存ボタンを押したかどうか分からなくなり、もう一度押してしまう（二重送信）
2. リストが長くなると、入力途中で誤って保存ボタンを押してしまい、その後さらに入力を続けて再度保存してしまう

**検討した対策案**：
- POST-Redirect-Get（PRG）パターンの導入（`flash`メッセージ機能と`app.secret_key`が必要になる）
- 未入力の品目がある場合に警告を出す方式（→却下。3章の代替フローで「入力を飛ばす（スキップ）」ことが正当な操作として認められているため、空欄の理由を機械的に判別できない）
- 訂正済みセルの色付けのみで対応する案（→根本解決にはならないため補助的な位置づけに留める）

**採用した対策**：
- `/input`で値を変更した行は、JavaScriptで背景色を変更し、どこを変更したか視覚的に分かるようにする
- 保存ボタン押下時に確認ダイアログ「今週分として更新しますが、よいですか？」を表示する（3-6参照）。「今週分」という言葉で、まだ入力途中であればここで気づけるようにする
- 確認ダイアログでOKした場合、ボタンを`disabled`にし「保存中...」に表示を変更することで、連続クリックによる二重送信を防ぐ

`app.secret_key`やセッション機能を新たに導入せず、HTML・JavaScriptのみで完結する対策とした点が、MVPのシンプルさを保つ上でのポイントである。

**見送った対策**：空欄・スペースのみの「買ってほしいもの」入力時の警告表示については、DBに保存されない（データの整合性は保たれる）こと、実害が軽微であることから、対応を見送ることとした。

## 14. 誤操作防止・デザイン方針（v3.0で新設）

### 14-1. 誤操作防止の方針

実際のテスト運用を通じて発見された誤操作パターン（9-6参照）への対策として、以下の方針を採用する。

- 重要な操作（在庫保存、買い物完了、品目削除等）には、必ず確認ダイアログを1回挟む
- 入力内容が変更されたことが視覚的に分かるよう、変更箇所をハイライト表示する
- 連続クリックによる意図しない重複操作を防ぐため、確認後は操作ボタンを一時的に無効化する
- `app.secret_key`やセッション機能のような、MVPの規模に対して過剰な仕組みは導入せず、HTML・CSS・JavaScriptの範囲で完結する対策を優先する

### 14-2. デザイン方針

`/list`（買い物リスト画面）は高齢者が主な利用者であることを踏まえ、以下の方針でスタイルを設計する。

- 項目名（ラベル）と内容（実際の値）の文字サイズの差は最小限にとどめる。内容側の文字を過度に小さくしない
- 情報の区別は、文字サイズの大小ではなく、太さ・下線・薄いハイライト（背景色）を用いる
- 全体的に余白を十分に取り、情報を詰め込みすぎない
- ボタン（買い物完了、メモ追加、メモ削除等）は押しやすい大きさを保つ

**決定理由**：文字サイズの差を極端につけると、かえって内容（品目名・数量）自体が読みにくくなる場合がある。サイズ差を抑えつつ、太さ・下線・背景色といった別の視覚的要素で情報の階層を表現することで、実用性と可読性を両立させる。
