## 1. Purpose（目的）

何をもって「正しく動く」と判断するか、変更を本番に出す手順、障害のときの対応、デモ版の運用のルールを定義する。あわせて、今後の変更（生成AIへの依頼を含む）で守る点を引き継ぐ。

---

## 2. Scope（対象範囲）

- テストと動作確認の方法
- 変更を本番に出す手順
- 障害のときの確認と復旧
- 見本データの扱いなど、デモ版の運用

---

## 3. Out of Scope（対象外範囲）

- 監視ツールによる常時監視と、アラートの自動通知。理由：デモ用で、稼働の保証を求めないため（02 の 5.2）
- 構成上の障害対策は 05、画面のエラー表示は 04 で扱う

---

## 4. Assumptions（前提条件）

- 運用するのは開発者1人（SG-31）とする
- 実装は生成AIに依頼し、別の生成AIのレビューと、開発者の確認を経てから取り込む
- 公開版はデモ用で、見本のデータだけを入れる

---

## 5. Definition Details（定義内容）

### 5.1 Handoff Items to Detail Design（詳細設計への引き継ぎ事項）

| ID | Handoff Item（引き継ぎ事項） | Details / Background（詳細・背景） |
|---|---|---|
| HO-001 | 生成AIに実装を頼むときは、役割と完了条件を明記する | ・依頼には、目的・前提・対象範囲・変更してはいけない範囲・完了条件・確かめ方・止まる条件を入れる<br>・理由：依頼の範囲をはっきりさせ、結果を確かめやすくするため |
| HO-002 | 完了は、差分と実行結果で判断する | ・差分・テストの結果・画面で確かめた結果を見てから取り込む<br>・理由：テストが通っても、画面の表示の抜けは分からないため |
| HO-003 | 動作確認には、DB が使えない状態も含める | ・背景：DB を止めて確かめたところ、メッセージが出るまで約5分かかることが分かり、接続の待ち時間に上限を設けた（05 の 5.4） |
| HO-004 | 新しいテストの根拠は、設計書（01〜06）にする | ・既存のテストのコメントは、凍結した decisions の章番号を根拠として書いている。現在の仕様の正本は設計書のため、新しく足すテストは設計書を根拠にする |

### 5.2 Implementation Constraints and Notes（実装時の注意点・制約）

- **秘密の値**（DB の接続先・パスワード・SECRET_KEY）は、コード・チャット・コマンドの行・ファイルに書かない。ローカルは `.env`、本番は Vercel の環境変数に置く
- **Git に入れないもの**：`.env`、仮想環境、DB のファイル（`*.db`）、キャッシュ、作業用の差分ファイル。`.gitignore` で除外している
- **リポジトリは Public**：コミットの前に、秘密の値や個人の情報が入っていないか確かめる
- **SQL** はプレースホルダを使い、文字列をつなげて組み立てない
- **エラー**は握りつぶさず、詳細はサーバーのログに残し、画面には決まったメッセージだけを出す

### 5.3 Test Policy and Acceptance Criteria（テスト方針・受け入れ基準）

| Type（種別） | Policy / Criteria（方針・基準） |
|---|---|
| Unit Test（単体テスト） | ・pytest で、計算（20件）と入力チェック（17件）を確かめる<br>・境目の値を必ず入れる（在庫数の 0・9999・10000、品目名と単位の 100・101 文字、0.5 未満の端数の切り上げ など）<br>・基準：取り込む前に、すべて成功し、ruff の指摘がないこと |
| Integration Test（結合テスト） | ・画面と DB を通した自動テストは、まだない（TBD-001） |
| System Test（システムテスト） | ・ローカルで、変更した画面と主な流れ（在庫入力 → 買い物リスト → 買い物完了）を操作して確かめる<br>・DB の扱いを変えたときは、アプリを起動した後に PostgreSQL を止めて、エラーのメッセージが出ることを確かめる（止める・戻すには管理者の PowerShell が要る）<br>・プレビューで、変更した部分を確かめる |
| Acceptance Test（受け入れテスト） | ・本番をスマートフォンで開き、01 の成功基準（SC-001〜003）を満たすことを確かめる |

### 5.4 Deployment and Release Overview（デプロイ・リリース手順概要）

| Step（ステップ） | Task（作業内容） | Owner（担当） |
|---|---|---|
| 1 | main を最新にし、作業用のブランチを作る | SG-31 |
| 2 | 実装し、レビューする | 実装：生成AI<br>レビュー：別の生成AI |
| 3 | ローカルで確かめる（5.3 の単体テスト・ruff・システムテスト） | SG-31 |
| 4 | ブランチにコミットして push する。コマンドは1行ずつ実行し、ブランチにいることを確かめてからコミットする | SG-31 |
| 5 | Vercel が作るプレビューで確かめる。設計書だけの変更は、GitHub のブランチの画面で図や表の表示を確かめる | SG-31 |
| 6 | main に取り込んで push する（Vercel が本番を自動で更新する） | SG-31 |
| 7 | Vercel の画面で、本番の Status が Ready になり、Source が今回のコミットになったことを確かめ、本番を一度開く | SG-31 |
| 8 | 作業用のブランチを消す | SG-31 |

- プレビューは本番と同じ DB を使う（05 の 5.6）。プレビューでデータを変えたら、元に戻す
- 本番に問題が出たときは、Vercel の画面の「Instant Rollback」で直前の本番に戻せる。使ったことはない

### 5.5 Monitoring, Alerts, and Incident Response（監視・アラート・障害対応方針）

| Aspect（観点） | Policy / Procedure（方針・手順） |
|---|---|
| Monitoring Targets and Methods（監視対象・監視方法） | ・常時の監視はしない<br>・応募書類を送る前と面接の直前に、本番を開いて表示を確かめる |
| Alert Recipients and Conditions（アラート通知先・条件） | ・Vercel・Neon・GitHub からのメール（公開の失敗、無料プランの条件の変更、使っているライブラリの弱点の警告など）を SG-31 が受け取る |
| Incident Confirmation Procedure（障害確認手順） | ・サイトが開けない・エラーが出る：Vercel の Deployments と Logs を見る。Neon の画面で DB が動いているかを見る |
| Recovery Procedure（復旧手順） | ・秘密の値が漏れたおそれがある：Neon のパスワードを作り直して Vercel の `DATABASE_URL` を入れ直し、`APP_PASSWORD`・`SECRET_KEY` も新しい値に変える<br>・公開した変更に問題がある：ブランチで直して出し直すか、Instant Rollback で戻す<br>・データがおかしい：見本データを入れ直す（5.6）<br>・ライブラリの弱点の警告：requirements.txt の版を上げ、5.4 の手順で出す |
| Escalation（エスカレーション先） | 対象外。理由：個人で運用するため。Vercel の使い方は講師に相談できる |

### 5.6 Operational Constraints and Maintenance（運用上の制約・定期メンテナンス）

#### 見本データの入れ直し

- **いつ**：応募書類を送る前、面接の直前、だれかに見てもらった後。ログイン状態は見た人のブラウザに30日残り、DB を入れ直してもログアウトされないため、見る直前に入れ直す
- **どう**：本番の DB に対して `scripts/seed_demo.py` を実行する。接続先はターミナルの環境変数に一時的に入れ、`.env` は書き換えない（戻し忘れて、手元の作業で本番のデータを消すのを防ぐため）。作業の後は環境変数を消す
- **スクリプトの安全策**：実行前に接続先（ホスト名と DB 名。パスワードは出さない）を表示し、`yes` と入力したときだけ実行する。削除と登録を1回の処理にまとめ、途中で失敗したら何も変えない
- **入るデータ**：品目6件、消費量の記録24件（7日ごとに4回分）、買ってほしいもの2件

#### サービスの条件

- Neon の無料プランは、5分使われないと休止する。休止明けの最初の表示は、少し時間がかかる
- Vercel が Python 3.13 の扱いをやめると、使う版を上げる必要がある。時期は未確定
- データの保管期間・バックアップ：対象外。理由：見本のデータだけで、いつでも入れ直せるため
